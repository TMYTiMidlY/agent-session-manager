# 2026-10-05：DSH 真实历史检索验收

环境：Linux x86_64、Node 24.21.0、Bun 1.4.2。最终 discovery 选中 **2,011 个会话**（包含子会话，仅最高代），不是只按项目顶层目录估算的主会话数。真实历史只读；派生缓存放在仓库 ignored 的 `.scratch/`，未修改、迁移或裁剪源历史。没有将会话正文、ID、绝对来源路径提交到本记录。

## 最终结果

计时 `/usr/bin/time`，候选 Node 单文件 bundle，默认 2 workers。全库查询使用 `--no-early-exit` 强制扫完整工作集，不用 limit 达成后返回来冒充全扫描提速。

| 场景 | 秒 | 峰值 RSS KiB | 默认 stderr 诊断行 |
|---|---:|---:|---:|
| 旧 npm v0.4.2 `list --agent dsh` 本次复现 | 9.55 | 301,816 | 0 |
| 新 `list --agent dsh --json` | 1.20 | 147,212 | 0 |
| 新全库查询，文本索引已就绪 | 4.71 | 328,728 | 0 |

同一查询从未带 Bloom 的早期派生索引升级、再热查询，输出 SHA256 相同；上述单会话与提前终止查询也返回相同 hit。默认附件 notice 没有淹没 stdout；verbose/quiet 行为另有合成回归。

## 不隐藏冷成本

- 没有缓存的全量原始扫描仍约 **116 秒**；第一次生成早期文本索引（4 workers）实测 **146.66 秒 / RSS 1,448,596 KiB**。更多 workers 未让这个语料的冷吞吐改善，也增加多 heap 内存，所以最终默认取 2，并提供 `-j 1`。
- 早期完整 timeline 缓存热查询仍 20.99 秒、约 1 GiB，已放弃。改为规范 search text + 小型三字符 Bloom sidecar，负候选不需重新解压原日志、JSON 解析大工具 payload 或重建 timeline。
- 将已有文本索引升级到最终 Bloom 方案首次花费 70.24 秒，后续完整查询 4.71 秒。首次建索引不承诺秒级；短关键词不足三个 UTF16 单元不能依靠三字符 Bloom，可能较慢。命中候选仍会读取规范源以保留完整工具详情。
- 用户给出的旧全库 123.15 秒/438MB 是问题报告的观测，不当成此次最终语料规模下重新控制变量测得的基线。

## 正确性闸门

- TypeScript strict typecheck；**275 项 Vitest 全通过**。
- Node bundle 与实际 Linux x64 Bun compiled artifact 均通过 CLI smoke：版本、metadata/cwd、current、角色与索引、多帧、checksum、任意损坏尾部的严格全读/有界 header 采样、缓存失效以及 worker 退出。
- Unicode/转义/UTF16 surrogate 匹配与 Bloom 负筛均有回归；缓存元数据/摘要损坏、只读/不可用缓存、源变化、SQLite WAL 绕开缓存、active/idle worker exit 均覆盖。
- 不把 `subarray` 累计 suffix 长度误报成 Node 的二次方复制：本机 Node 接原 buffer 指针，每帧 decoder 初始化/分配/事件投影才是主要 CPU 成本。增量 frame scanner 同时修复全文件采样与 Node/Bun 多帧/截断语义差异。

结论：不需要重写原生 DSH 历史目录；应优化只读消费端。需要长期进一步优化冷扫描时，优先复用受支持的 decoder context 或让规范投影增量化，不引入未经验证的 runtime 私有 handle，不用 raw JSON grep 替代转录语义。
